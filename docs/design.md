# Blind Auction 설계 문서 v2

> 작성일: 2026-10-07
> 원본: Notion "Blind Auction 설계 문서 v2". 둘이 다르면 함께 고친다.
> 피드백이 없으면 이 문서를 기준으로 개발을 진행한다. 개발 중 정해지는 세부사항(이벤트 항목, API 주소)은 이 문서에 추가한다.

## 1. 개요

NFT를 ETH로 비공개 입찰하는 경매. 입찰가는 해시로 숨겨서 내고(Commit), 입찰 기간이 끝난 뒤 각자 공개한다(Reveal). NFT와 ETH의 교환은 스마트 컨트랙트가 보장한다.

## 2. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 컨트랙트 | Solidity, Hardhat | Outline 지정 |
| 컨트랙트 라이브러리 | OpenZeppelin (ERC-721, 재진입 잠금) | NFT 표준(ERC-721)과 재진입 잠금은 직접 만들지 않고, 많은 프로젝트가 쓰며 보안 검토를 거친 OpenZeppelin 코드를 가져다 쓴다. 컨트랙트는 배포 후 고칠 수 없어서, 직접 만든 코드의 버그가 곧 자산 손실로 이어지기 때문이다 |
| Backend | TypeScript, Express | TypeScript는 Outline 지정. 프레임워크는 자유인데, Express를 써 본 경험이 있고 조회 API 몇 개라 큰 프레임워크가 필요 없다 |
| 블록체인 연결 | ethers.js | Outline 지정 |
| DB | PostgreSQL (Docker Compose로 실행) | Outline 지정. Docker로 누구나 같은 환경에서 실행할 수 있다 |
| 테스트 | Hardhat 테스트(컨트랙트), Vitest + Supertest(통합) | Hardhat에 테스트와 시간 이동 기능이 들어 있다. Vitest는 TypeScript를 바로 쓸 수 있고 Supertest로 API 요청을 테스트할 수 있다 |
| 네트워크 | 로컬 Hardhat 노드 | 테스트넷 ETH 없이 개발·시연할 수 있고, 블록 시간을 앞당겨 기간 관련 테스트를 할 수 있다 |
| 경매용 NFT | 테스트용 NFT 컨트랙트 | 경매 대상의 의미는 과제 범위가 아니므로 테스트용으로 발행해서 쓴다 |

## 3. 시스템 구성

| 구성 요소 | 하는 일 |
|---|---|
| 스마트 컨트랙트 | 경매 규칙을 실행하고 NFT와 ETH를 보관한다. 결과는 이벤트로 남긴다 (원본) |
| Indexer | 이벤트를 읽어 DB에 저장한다 |
| PostgreSQL | 검색하기 쉽게 모아 둔 사본 |
| Backend API | DB를 조회해서 돌려준다 (조회 전용) |
| 사용자 스크립트 | 경매 생성, 입찰, 공개, 종료, 출금 트랜잭션을 보낸다 (12번) |
| 웹 화면 (시연용) | 조회는 API로 하고, 쓰기는 브라우저에서 컨트랙트로 직접 보낸다 (17번) |

```
[쓰기] 사용자 스크립트(지갑) ──트랜잭션──▶ 컨트랙트 ──이벤트──▶ Indexer ──▶ PostgreSQL
[읽기] 사용자 ◀──── API ◀─────────────────────────────────────────── PostgreSQL
```

- 쓰기는 사용자 지갑에서 컨트랙트로 직접 보낸다. API가 대신 보내면 서버가 돈이나 개인키를 가져야 하고, msg.sender가 서버 주소가 되어 누가 입찰했는지 구분할 수 없다.
- 블록체인에는 SQL 같은 검색이 없고, 과거 기록은 이벤트로만 남는다. 그래서 Indexer가 이벤트를 DB에 모으고 API는 DB를 조회한다.
- 블록체인과 DB가 다르면 블록체인이 맞다. DB는 블록체인을 다시 읽어 맞춘다.

**실행 구성**

| 프로세스 | 실행 방법 |
|---|---|
| Hardhat 노드 | 로컬 블록체인. 컨트랙트를 배포한다. 개발용(`npm run node`)은 트랜잭션이 없어도 5초마다 빈 블록을 만든다 (10번) |
| PostgreSQL | Docker Compose |
| Indexer | 별도 프로세스 |
| API | 별도 프로세스. 시연용 웹 화면 파일도 함께 제공한다 (17번) |

- Indexer와 API는 따로 실행한다. 통합 테스트에서 Indexer를 껐다가 다시 켜야 하는데, 묶여 있으면 API도 같이 꺼진다. 따로 두면 Indexer가 멈춰도 API는 계속 조회할 수 있다.
- 테이블 정의는 db/에 SQL 파일로 한 번만 두고, Indexer와 API가 같은 테이블을 쓴다.
- 테이블은 `npm run db:init`으로 만든다. SQL이 IF NOT EXISTS라 여러 번 실행해도 안전하다. Docker 초기화 폴더(docker-entrypoint-initdb.d)는 볼륨이 비어 있을 때 한 번만 실행되어, 이미 만든 DB에 적용하거나 통합 테스트에서 테이블을 다시 만들 수 없어서 쓰지 않는다.
- Node 패키지는 두 개다. contracts/는 Hardhat 전용 패키지로 따로 두고, db/·indexer/·api/·tests/는 루트 package.json 하나를 같이 쓴다. Indexer와 API는 프로세스만 다르고 DB 연결, 환경 변수 읽기 같은 코드와 의존성(pg, TypeScript)이 같아서, 폴더마다 패키지를 두면 설치와 설정만 늘어난다.

**폴더 구조**

```
contracts/                Hardhat 패키지
  contracts/              BlindAuction.sol, MockNFT.sol, test/ReentrantBidder.sol(테스트용 재진입 공격 컨트랙트)
  tasks/                  사용자 스크립트 명령 (Hardhat task, npm run <이름>)
  scripts/lib/            사용자 스크립트의 실제 처리 (task와 demo가 같이 쓴다)
  test/                   컨트랙트 단위 테스트, test/scripts/ 스크립트 테스트
indexer/                  이벤트 수집 → DB (main.ts), 복구 명령 (reset.ts)
api/                      조회 API (Express)
db/                       테이블 생성 SQL (schema.sql), db:init
tests/                    통합 테스트 (integration/), 테스트 도우미 (helpers/)
web/                      시연용 웹 화면 (API가 정적 파일로 제공, 17번)
docs/                     설계 문서
docker-compose.yml        PostgreSQL
package.json              db/·indexer/·api/·tests/가 같이 쓰는 루트 패키지
README.md
```

## 4. 경매 규칙

| # | 규칙 | 이유 |
|---|---|---|
| Q1 | 경매 대상은 NFT | 블록체인 밖의 물건은 전달을 보장할 수 없다. NFT는 컨트랙트가 보관했다가 낙찰자에게 직접 넘길 수 있다 |
| Q2 | 판매자가 기간을 정한다. 입찰 10분~5일, 공개 1일~2일 | 공개는 모든 입찰자가 직접 해야 하므로 여유 있게 둔다 |
| Q3 | 입찰가는 해시로 숨기고, 보증금이 입찰가 이상이어야 유효 | 입찰가를 숨기면서도 낙찰자가 실제로 낼 수 있는 돈을 미리 확보한다 |
| Q3-1 | 무효 입찰(보증금이 입찰가보다 적음)은 보증금 전액 반환 | 규칙을 어긴 게 아니라 조건을 못 맞춘 것이므로 돌려준다 |
| Q4 | 공개하지 않으면 보증금 몰수, 판매자에게 | 남의 공개를 보고 불리하면 빠지는 행동을 막는다. 여러 지갑으로 입찰하고 골라서 공개해도 손해가 되게 한다 |
| Q5 | 최고가 낙찰, 동점이면 먼저 입찰한 사람 | 동점일 때 결과가 하나로 정해져야 한다 |
| Q6 | 낙찰자는 NFT와 차액, 판매자는 낙찰가와 몰수금, 나머지는 보증금 전액. 장부에 적고 각자 출금 | 7번, 13번 참고 |
| Q7 | 유효 입찰이 없으면 NFT는 판매자에게 돌아가고 정상 종료 | 입찰자가 없어도 경매가 끝나야 한다 (Outline 요구사항) |
| Q8 | 종료는 누구나 호출할 수 있다 | 판매자만 호출할 수 있으면, 결과가 마음에 안 드는 판매자가 호출하지 않아 모든 보증금이 묶일 수 있다 |
| Q9 | 판매자의 입찰은 막지 않는다 | 다른 지갑으로 입찰하면 우회되므로 막아도 의미가 없다 |
| Q10 | 지갑당 한 경매에 1회 입찰 | 구조가 단순해지고, (경매, 입찰자)가 하나뿐이라 중복 방지가 쉽다 |
| Q11 | 해시 = 입찰가 + secret + 입찰자 주소 | 남의 해시를 복사해 입찰해도 주소가 달라 공개할 수 없다 |

## 5. 경매 단계

| 단계 | 누가 | 보내는 것 | 컨트랙트가 하는 일 |
|---|---|---|---|
| 입찰 | 입찰자 | 해시 + 보증금 | 해시, 보증금, 입찰 순서를 저장한다. 보증금은 컨트랙트가 보관한다 |
| 공개 | 입찰자 본인 | 입찰가 + secret | 입찰가 + secret + msg.sender로 해시를 다시 계산해 저장된 해시와 비교한다. 다르면 실패. 같으면 보증금이 입찰가 이상일 때 유효, 아니면 무효. 결과를 장부에 반영한다 (7번) |
| 종료 | 누구나 | 없음 | 유효 입찰이 있으면 NFT를 낙찰자에게 보내고 판매자와 낙찰자 몫을 장부에 적는다. 없으면 NFT를 판매자에게 돌려준다 |
| 출금 | 장부에 돈이 있는 사람 | 없음 | 장부를 0으로 만든 뒤 송금한다 |

컨트랙트는 스스로 실행되지 않는다. 공개 기간이 끝나도 누군가 종료를 호출해야 정산된다.

## 6. 컨트랙트 함수

| 함수 | 누가 | 언제 | 이벤트 |
|---|---|---|---|
| 경매 생성 | NFT 주인 | 언제나 | 경매 생성됨 |
| 입찰 | 누구나 (지갑당 1회) | 입찰 기간 | 입찰됨 |
| 공개 | 입찰자 본인 | 공개 기간 | 공개됨 |
| 종료 | 누구나 | 공개 기간이 끝난 뒤, 1회 | 종료됨 |
| 출금 | 장부에 돈이 있는 사람 | 언제나 | 출금됨 |

- 이벤트에 담을 정보는 10번 DB 칼럼을 기준으로 개발 시작 전에 정한다. Indexer가 이벤트 하나만 보고 DB를 채울 수 있어야 한다.
- 예: 종료됨 이벤트에는 낙찰자 주소가 있어야 Indexer가 입찰마다 낙찰·패찰을 정할 수 있다.

**이벤트 항목** (10번 DB 칼럼 기준. Indexer는 이벤트만 보고 DB를 채운다)

| 이벤트 | 항목 (★ = indexed) | 채우는 DB 칼럼 |
|---|---|---|
| 경매 생성됨 `AuctionCreated` | auctionId★, seller★, nft★, tokenId, biddingEnd, revealEnd | auctions: 경매 번호, 판매자, NFT 주소, 토큰 번호, 입찰 마감, 공개 마감 |
| 입찰됨 `BidCommitted` | auctionId★, bidder★, commitment, deposit | bids: 경매 번호, 입찰자 주소, 해시, 보증금. 결과 = 미공개 |
| 공개됨 `BidRevealed` | auctionId★, bidder★, value, valid | bids: 공개 여부, 입찰가, 결과 = 유효 또는 무효 |
| 종료됨 `AuctionFinalized` | auctionId★, winner★, winningBid, forfeited | auctions: 종료 여부, 낙찰자, 낙찰가, 몰수금. bids: 낙찰자의 입찰 = 낙찰, 나머지 유효 입찰 = 패찰 |
| 출금됨 `Withdrawn` | account★, amount | 저장하지 않는다 (10번) |

결과 칼럼이 바뀌는 순서:

| 이벤트 | 결과 |
|---|---|
| 입찰됨 | 미공개 |
| 공개됨 | valid가 true면 유효, false면 무효 |
| 종료됨 | 유효 중 winner의 입찰은 낙찰, 나머지는 패찰. 무효는 그대로 무효, 미공개는 그대로 미공개(몰수) |

- 유효 입찰이 없으면 winner는 0 주소이고 winningBid는 0이다. DB의 낙찰자는 비워 둔다(NULL).
- 입찰 순서(seq)와 장부 금액은 이벤트에 넣지 않는다. 조회 요구사항(11번)에 쓰는 곳이 없고, 동점 판정은 컨트랙트가 이미 끝냈으므로 Indexer는 그 결과(winner)만 옮기면 된다.
- 블록 시간은 이벤트가 아니라 이벤트가 들어 있는 블록에서 읽는다 (indexer_state).
- indexed 항목은 로그의 topic(검색용 칸)에 들어가서 경매 번호나 주소로 걸러 요청할 수 있다.

## 7. 정산

**반환은 종료 때가 아니라 공개 때 장부에 적는다.** 종료 때 한꺼번에 처리하면 입찰자 전체를 반복문으로 돌아야 하고, 트랜잭션의 가스 상한 때문에 입찰자가 많으면 종료가 실행되지 않는다. 공개는 한 명씩 들어오므로 그때 결과를 적으면 반복문이 필요 없다.

| 공개 결과 | 장부에 적는 것 |
|---|---|
| 무효 | 그 사람 보증금 전액 |
| 유효, 현재 최고가보다 낮음 (또는 같은데 나중에 입찰함) | 그 사람 보증금 전액 |
| 유효, 현재 최고가보다 높음 (또는 같은데 먼저 입찰함) | 새 최고가가 된다. 밀려난 이전 최고가의 보증금 전액을 적는다 |

공개 순서와 입찰 순서는 다르다. 먼저 입찰한 사람이 나중에 공개할 수 있으므로, 컨트랙트는 입찰 순서를 저장해 두고 동점일 때 비교한다 (Q5).

종료 때 적는 것은 두 가지다.
- 낙찰자: 보증금 − 낙찰가
- 판매자: 낙찰가 + 몰수금. 몰수금 = 보증금 전체 합계 − 공개된 보증금 합계 (반복문 없음)
- 유효 입찰이 없으면 낙찰가는 0이고, 판매자는 NFT를 돌려받고 몰수금만 받는다.

**예시** (공개 순서 A → B → C, D 미공개)

| 입찰자 | 보증금 | 입찰가 | 결과 | 장부 |
|---|---|---|---|---|
| A | 5 | 3 | B에게 밀림 | 5 (B 공개 때) |
| B | 4 | 4 | 낙찰 | 0 (종료 때) |
| C | 2 | 3 | 무효 | 2 (C 공개 때) |
| D | 3 | 미공개 | 몰수 | - |
| 판매자 | | | | 4 + 3 = 7 (종료 때) |

장부 합계 14 = 보증금 합계 14. 컨트랙트에 남거나 모자라는 돈이 없다.

## 8. 데이터 설계 (온체인/오프체인, 공개/비공개)

| 데이터 | 위치 | 공개 여부 |
|---|---|---|
| 경매 정보, 해시, 보증금, 장부, 결과 | 온체인 (컨트랙트) | 공개. 블록체인 데이터는 누구나 볼 수 있다 |
| 입찰가 | 공개 전: 입찰자 본인만 / 공개 후: 온체인 | 공개 단계 전까지 비공개 |
| secret | 입찰자 본인 컴퓨터 (스크립트는 `.bids/` 파일, 웹 화면은 브라우저 저장소에 저장) | 비공개. 서버·DB·Git에 저장하지 않는다 |
| 경매·입찰 조회용 사본 | 오프체인 (PostgreSQL) | 공개 데이터만 담는다 (이벤트를 옮긴 것) |

- 블록체인 데이터는 전부 공개되므로, 입찰가는 해시로만 올린다.
- secret과 입찰가를 서버나 DB에 두면 관리자, 해킹, API 버그 중 하나만으로 공개 전에 입찰가가 드러나고, 서버가 다시 믿어야 하는 진행자가 된다.
- secret을 잃어버리면 공개할 수 없고, 보증금은 몰수된다 (Q4). 보관은 입찰자 책임이다.

## 9. Indexer

- 컨트랙트 이벤트를 블록 범위로 요청해 읽고 DB에 저장한다. 새 블록이 생길 때마다 계속 읽는다.
- **중단 후 복구**: 마지막으로 처리한 블록 번호(책갈피)를 DB에 저장한다. 다시 켜지면 그다음 블록부터 읽는다.
- **중복 방지**: (경매 번호), (경매 번호, 입찰자 주소)에 UNIQUE를 걸고, 중복이면 건너뛴다(ON CONFLICT DO NOTHING).
- 이벤트 저장과 책갈피 저장은 한 DB 트랜잭션으로 묶는다. 둘 중 하나만 저장되는 일이 없다.
- 노드의 chain id는 설정(CHAIN_ID, 기본 31337 = Hardhat)으로 미리 준다. ethers가 네트워크를 스스로 알아내려 하면 노드가 꺼져 있을 때 자체 재시도와 로그를 끝없이 반복하는데, 미리 주면 노드 장애가 일반 요청 오류로 와서 Indexer의 재시도로 처리된다.
- 노드나 DB 오류가 나면 RETRY_DELAY_MS(기본 5초)만큼 기다렸다가 같은 블록 범위를 다시 처리한다. 실패한 범위는 책갈피가 움직이지 않으므로 다시 처리해도 빠지는 이벤트가 없다.
- **하나만 실행**: 같은 DB에는 Indexer가 하나만 돈다. 시작할 때 PostgreSQL advisory lock(`pg_try_advisory_lock`)을 전용 연결로 잡고 프로세스가 끝날 때까지 유지한다. 이미 잡혀 있으면 "Indexer가 이미 실행 중"이라는 안내와 할 일, 잠금을 가진 연결(pid)을 출력하고 멈춘다(종료 코드 1). 잠금은 연결에 붙어 있어서 프로세스가 강제 종료돼도 PostgreSQL이 스스로 푼다. 남는 잠금 파일이 없다.
- **시작할 때 확인**: Indexer는 시작할 때 다음을 확인한다. CONTRACT_ADDRESS에 컨트랙트가 있는가, DEPLOY_BLOCK이 체인의 최신 블록 이하이고 실제 배포 블록 이하인가, DB 책갈피가 최신 블록 이하인가. 하나라도 틀리면 원인과 할 일을 한국어로 출력하고 멈춘다(종료 코드 1). 설정이 틀린 것은 재시도해도 낫지 않아서, 그대로 두면 같은 오류를 끝없이 반복하거나(예: DEPLOY_BLOCK이 늦어 경매 생성 이벤트를 놓친 뒤 입찰을 저장할 때 나는 외래 키 오류) 아무 일도 하지 않고 기다리기 때문이다. 노드나 DB에 연결이 안 되는 것은 위와 같이 재시도한다. DEPLOY_BLOCK이 실제 배포 블록보다 앞이면 빈 블록을 더 읽을 뿐 결과가 같으므로, 실제 배포 블록을 알려 주기만 하고 진행한다. 실제 배포 블록은 "그 블록에서 주소에 코드가 있는가"를 이진 탐색해 찾는다. 이 확인으로도 감지하지 못하는 경우가 있다 (16번).

**장애 상황**

| 상황 | 처리 |
|---|---|
| Indexer가 꺼짐 | 다시 켜면 책갈피 다음 블록부터 읽어 빠진 이벤트를 채운다 |
| DB 연결이 끊김 | 트랜잭션이 취소되어 반쯤 저장된 데이터가 없다. 책갈피도 그대로라 다시 연결되면 같은 블록부터 다시 처리한다 |
| 블록체인 노드 연결이 끊김 | 잠시 기다렸다가 다시 시도한다 |
| Indexer가 두 개 켜짐 | 두 번째는 시작할 때 잠금을 잡지 못해 안내 후 멈춘다(위 "하나만 실행"). 둘이 같이 돌면 책갈피 하나를 같이 쓰면서 이벤트가 빠질 수 있다. 한쪽이 아직 커밋하지 않은 입찰을 다른 쪽의 공개·종료 UPDATE가 보지 못한 채 책갈피가 그 블록을 지나가고, CONTRACT_ADDRESS가 서로 다르면 한쪽이 다른 쪽 컨트랙트의 블록까지 처리한 것으로 표시하기 때문이다. 이미 빠졌으면 하나만 남기고 `npm run indexer:reset` 후 다시 켠다 |
| Indexer의 잠금 연결만 끊김 (DB 재시작, 네트워크) | PostgreSQL이 잠금을 푼다. Indexer는 동기화를 멈추고 다음 단계 전에 다시 연결해 잠금을 잡은 뒤 책갈피부터 이어서 읽는다. 그 사이에 다른 Indexer나 `indexer:reset`이 잠금을 가져갔으면 멈춘다(종료 코드 1). 각 동기화 트랜잭션도 COMMIT 직전에 잠금이 아직 자기 것인지 확인하고, 아니면 되돌린다 |
| DB가 블록체인과 다르다고 의심됨 | Indexer를 멈추고(켜져 있으면 reset이 같은 잠금을 확인해 비우지 않고 거부한다) `npm run indexer:reset`으로 책갈피와 auctions·bids를 한 트랜잭션으로 비운 뒤 Indexer를 다시 켠다. 배포 블록부터 다시 읽어 사본을 새로 만들므로, 빠진 행뿐 아니라 잘못 저장된 행도 블록체인과 같아진다. 책갈피만 돌리면 이미 있는 행은 UNIQUE와 조건부 UPDATE 때문에 건너뛰어 잘못된 값이 남는다 |
| 로컬 노드를 다시 켬 (체인이 처음부터 시작) | Indexer를 멈추고 `npm run deploy`로 다시 배포한 뒤, 출력된 CONTRACT_ADDRESS·DEPLOY_BLOCK으로 `.env`를 갱신하고 `npm run indexer:reset` 후 Indexer를 다시 켠다. 이전 체인의 데이터가 DB에 남고, 책갈피가 새 체인의 블록 번호보다 앞서 있어 그 아래의 새 이벤트를 건너뛰기 때문이다. 이 절차를 빠뜨리면 Indexer가 시작할 때 감지하고 멈춘다(컨트랙트 없음, DEPLOY_BLOCK이나 책갈피가 새 체인보다 앞섬). 단, 새 체인의 블록 수가 예전 책갈피를 넘은 뒤에는 감지하지 못한다 (16번) |
| CONTRACT_ADDRESS·DEPLOY_BLOCK이 틀림 | 시작할 때 멈추고 원인과 할 일을 알려 준다. 주소에 컨트랙트가 없으면 배포한 뒤 `.env`를 고친다. DEPLOY_BLOCK이 실제 배포 블록보다 뒤이면 알려 준 실제 배포 블록으로 고치고, 이미 저장된 데이터가 있으면 `npm run indexer:reset` 후 다시 켠다 |

## 10. DB 테이블

| 테이블 | 칼럼 | 출처 이벤트 |
|---|---|---|
| auctions | 경매 번호, 판매자, NFT 주소, 토큰 번호, 입찰 마감, 공개 마감 | 경매 생성됨 |
| | 종료 여부, 낙찰자, 낙찰가, 몰수금 | 종료됨 |
| bids | 경매 번호, 입찰자 주소, 해시, 보증금 | 입찰됨 |
| | 공개 여부, 입찰가, 결과(유효·무효·낙찰·패찰·미공개) | 공개됨, 종료됨 |
| indexer_state | 마지막 처리 블록 번호, 그 블록의 시간 | Indexer |

- 사용자 테이블은 두지 않는다. 보증금·입찰가·결과는 사람이 아니라 "그 사람이 그 경매에 한 입찰"에 붙는 정보다.
- 출금됨 이벤트는 조회 요구사항에 필요한 곳이 없어 저장하지 않는다.
- 금액은 wei 단위로 저장하고 API에서는 문자열로 돌려준다. 1 ETH = 10의 18제곱 wei인데, JavaScript 숫자는 약 9천조(2의 53제곱)까지만 정확해서 큰 금액을 숫자로 다루면 끝자리가 틀어진다. DB에는 큰 수를 정확히 담는 NUMERIC 타입으로 저장한다.
- 주소는 소문자로 통일해 저장하고 검색한다. 같은 지갑 주소도 대소문자가 섞여 들어오는 경우가 있어서, 통일하지 않으면 "참여한 경매" 검색에서 같은 사람을 놓친다.
- 결과는 영어 코드로 저장하고 API도 같은 값을 돌려준다: unrevealed(미공개), valid(유효), invalid(무효), won(낙찰), lost(패찰). 코드와 SQL에서 다루기 쉽고, 화면 표시용 한국어 이름은 쓰는 쪽에서 바꾸면 되므로 저장 값과 표시를 나눈다.
- 시간(입찰 마감, 공개 마감, 블록 시간)은 unix 초(BIGINT)로 저장한다. 컨트랙트가 block.timestamp(unix 초)와 비교하는 값을 그대로 옮기면, 진행 상태를 컨트랙트와 같은 기준으로 계산할 수 있고 시간대 변환으로 어긋날 일이 없다.

**진행 상태는 저장하지 않고 계산한다.** 저장하면 시간이 지나도 값이 바뀌지 않아 실제와 어긋난다. 여기서 시간은 서버 시계가 아니라 블록 시간(indexer_state에 저장한 마지막 블록의 시간)이다. 컨트랙트가 블록 시간으로 단계를 판단하므로 같은 기준을 써야 어긋나지 않는다.

| 조건 | 상태 |
|---|---|
| 입찰 마감 전 | 입찰 중 |
| 입찰 마감 후 ~ 공개 마감 전 | 공개 중 |
| 공개 마감 후, 종료 안 됨 | 종료 대기 |
| 종료됨 | 종료 |

Hardhat 노드는 기본 설정에서 트랜잭션이 올 때만 블록을 만들어서, 아무도 트랜잭션을 보내지 않으면 블록 시간이 멈추고 API의 진행 상태도 실제와 어긋난다. 그래서 개발용 노드는 5초마다 빈 블록을 만든다(interval mining, `DEV_BLOCK_INTERVAL_MS`). 입찰 기간이 최소 10분이라 몇 초 늦는 것은 문제가 되지 않는다. 컨트랙트 테스트와 통합 테스트에서는 켜지 않는다. 시간을 지정한 블록과 트랜잭션 사이에 빈 블록이 끼어들면 경계값 테스트가 흔들리기 때문이다.

## 11. API

모두 조회 전용이다.
- 전체 경매 목록 / 진행 중인 경매 / 종료된 경매 (auctions에 상태 조건)
- 경매 상세 정보 / 진행 상태 / 결과 (auctions + bids)
- 특정 사용자가 참여한 경매 (bids에서 입찰자 주소로 찾고 auctions를 붙임)

**주소**

| 요구 | 주소 | 내용 |
|---|---|---|
| 전체 경매 목록 | `GET /auctions` | 경매 요약 목록. 최신 경매가 먼저 |
| 진행 중인 경매 | `GET /auctions?status=active` | bidding + revealing + awaiting_finalize |
| 종료된 경매 | `GET /auctions?status=finalized` | finalized |
| (단계별) | `GET /auctions?status=bidding` 등 | 상태 코드 4개 중 하나로도 거를 수 있다 |
| 경매 상세 / 진행 상태 / 결과 | `GET /auctions/:auctionId` | 경매 정보 + status + result + 입찰 목록(bids) |
| 특정 사용자가 참여한 경매 | `GET /users/:address/auctions` | 그 주소가 입찰한 경매 목록. 항목마다 그 사람의 입찰(myBid) |

- 진행 상태 코드: bidding(입찰 중), revealing(공개 중), awaiting_finalize(종료 대기), finalized(종료). 결과 코드와 같은 이유로 영어 코드를 쓴다 (10번).
- **종료 대기는 진행 중에 넣는다.** 공개 마감이 지났어도 종료가 호출되기 전에는 NFT와 대금이 넘어가지 않아 정산이 끝나지 않았고, "종료된 경매"를 컨트랙트에서 종료가 실제로 실행된 경매로 두면 컨트랙트 상태(Finalized)와 정확히 맞는다.
- 금액과 경매 번호는 문자열(wei), 주소는 소문자, 시간은 unix 초 숫자다 (10번). 요청의 주소는 대소문자가 섞여 있어도 소문자로 바꿔서 찾는다.
- 모든 응답에 `asOf: { blockNumber, blockTime }`를 넣는다. 진행 상태를 계산한 기준 블록 시간이고, 값이 오래 그대로면 Indexer가 멈췄다는 뜻이다.
- result는 종료 전에는 null이다. 유효 입찰 없이 종료되면 winner는 null, winningBid는 "0"이다.
- 오류: 경매 번호·주소·status 형식이 틀리면 400, 없는 경매는 404, Indexer가 아직 한 블록도 처리하지 않아 상태를 계산할 수 없으면 503.
- 페이지 나누기는 두지 않는다. 쓰기 API도 없다. 쓰기는 지갑에서 컨트랙트로 직접 보낸다 (3번).
- API 프로세스는 시연용 웹 화면 파일도 제공한다: `/`(화면), `/vendor/ethers.min.js`, `/deployment.json`. 모두 GET으로 파일을 내려줄 뿐이고, 위 조회 API의 주소와 응답은 바뀌지 않는다 (17번).

## 12. 사용자 스크립트

ethers.js 스크립트로 트랜잭션을 보낸다. 발표 시연용 웹 화면은 17번이다 (Outline상 프론트엔드는 필수 아님).

| 스크립트 | 하는 일 |
|---|---|
| 배포 | MockNFT와 BlindAuction을 로컬 노드에 배포하고 주소와 배포 블록을 기록한다. Indexer 설정(CONTRACT_ADDRESS, DEPLOY_BLOCK)에 넣을 값을 출력한다. 배포해야 나머지 스크립트를 쓸 수 있다 |
| 경매 생성 | NFT를 경매 컨트랙트가 가져갈 수 있게 승인(approve)한 뒤 경매를 만든다 |
| 입찰 | secret을 무작위로 만들고 해시를 계산한다. 입찰가와 secret을 본인 컴퓨터의 파일에 저장한 뒤 해시와 보증금을 보낸다 |
| 공개 | 저장한 파일에서 입찰가와 secret을 읽어 공개한다 |
| 종료, 출금 | 함수를 호출한다 |
| 시연용 | 테스트 NFT 발행, 블록 시간 앞당기기 |
| 시연 전체 실행(demo) | 7번 예시를 생성부터 출금까지 그대로 실행한다. 위 스크립트와 같은 함수를 쓰므로 새 기능이 아니라 실행 순서를 묶은 것이다. 시연 때 명령 수십 개를 순서대로 치다 틀리는 일을 없애고, 장부 합계가 7번과 같은지 바로 보여 준다. 장부는 경매별이 아니라 지갑별 합계라서, 시작할 때 이전 경매에서 남은 장부를 따로 기록·표시하고 이번 경매 몫과 섞이지 않게 검사한다 |

스크립트는 Hardhat task로 만들고 `cd contracts && npm run <이름> -- --옵션`으로 실행한다. 지갑은 로컬 노드 기본 계정 번호(`--account`)로 고르고, 금액은 ETH 단위, 기간은 `10m`, `1d`처럼 받는다.

스크립트는 실행 전에 배포 기록의 BlindAuction·MockNFT 주소에 컨트랙트가 있는지 확인한다. 없으면 노드를 다시 켠 경우로 보고 `npm run deploy`를 먼저 실행하라고 안내한다. 확인하지 않으면 빈 주소를 조회한 결과를 해석하지 못해 원인을 알기 어려운 오류(could not decode result data)가 난다.

입찰 스크립트는 secret 파일을 **트랜잭션을 보내기 전에** 저장한다. 보낸 뒤에 저장하면, 트랜잭션은 성공했는데 그 직후 프로그램이 죽었을 때 secret이 사라져 공개할 수 없고 보증금이 몰수된다 (8번). 파일은 `.bids/<chainId>-<컨트랙트>-<경매 번호>-<입찰자>.json`이고 입찰 하나에 하나다.

secret은 입찰할 때마다 무작위로 새로 만든다.

secret 파일(`.bids/`)은 Git에 올라가지 않도록 제외 목록(.gitignore)에 넣는다.

## 14. 테스트

**컨트랙트 단위 테스트**
- 정상 흐름: 생성 → 입찰 → 공개 → 종료 → 출금. 7번 예시로 장부 합계가 보증금 합계와 같은지 확인
- 규칙: 무효면 전액 반환(Q3-1), 동점이면 먼저 입찰한 사람(Q5, 나중에 공개해도), 유효 입찰이 없으면 NFT는 판매자에게(Q7)
- 실패해야 하는 경우:
  - 같은 지갑의 두 번째 입찰
  - 공개 기간에 입찰, 공개 마감 뒤 공개
  - 본인이 아닌 사람의 공개, 같은 입찰의 두 번째 공개
  - 공개 마감 전 종료, 두 번째 종료
  - NFT 주인이 아닌 사람의 경매 생성
  - 두 번째 출금은 받을 돈이 없음
  - 재진입 공격으로 돈이 더 빠져나가지 않음

**통합 테스트**
- 전체 흐름 후 API로 조회한 결과가 컨트랙트 상태와 같은지 확인
- Indexer를 끈 동안 입찰이 들어와도, 다시 켜면 빠짐없이 DB에 들어오는지 확인
- 같은 이벤트를 두 번 읽어도 DB에 한 번만 저장되는지 확인
- Indexer가 이미 실행 중이면 두 번째 Indexer가 안내 후 멈추는지, 첫 번째를 끄면 다시 시작할 수 있는지, Indexer 실행 중에는 `indexer:reset`이 거부되는지, 잠금 연결이 끊기면 다시 잡거나(다른 쪽이 잡았으면) 멈추는지

**웹 화면 (17번)**
- 화면 로직(상태 이름, 남은 시간, 금액 표시, Indexer 멈춤 판단)은 단위 테스트
- API가 화면 파일을 제공하는지, 조회 API는 그대로이고 쓰기 요청은 여전히 거절되는지
- 브라우저 모듈의 해시가 스크립트와 같은지, 입찰할 때 secret이 전송보다 먼저 저장되는지를 테스트 노드에서 확인
- 보내기 전 확인(기간, 두 번째 입찰, NFT 주인, 기간 범위, 종료 시점)에 걸리면 트랜잭션을 보내지 않는지, 손상·변조된 저장값과 다른 컨트랙트의 가져오기 파일을 거절하는지
- `?rpc=`가 이 컴퓨터의 노드 주소만 받는지, 노드의 chain id가 배포 기록과 다르면 연결하지 않는지
- 경매 진행 화면: 단계별 "다음에 할 일", 카드마다 나오는 버튼과 꺼진 이유, 체인에서 읽은 상태, "새 경매 시작"이 남은 NFT를 다시 쓰는지
- 실제 브라우저로 7번 예시를 경매 진행 화면에서 끝까지 실행하는 시연 체크리스트

## 16. 한계와 제외

- 보증금이 입찰가 이상이어야 해서, 보증금을 보면 입찰가의 상한이 드러난다.
- 보증금과 입찰가를 따로 내는 방식(C 방식)은 방치되는 금액을 처리할 규칙이 추가로 필요해서 제외했다.
- 제외: 경매 취소, 최저가
- 웹 화면은 발표 시연용이다 (17번). 로컬 노드가 열어 둔 테스트 계정으로 서명하고 지갑(MetaMask 등) 연동은 하지 않는다. 실제 네트워크에서 쓰려면 지갑 연동이 필요하다.
- 웹 화면의 secret은 브라우저 저장소에 암호화하지 않고 둔다. 같은 컴퓨터의 다른 사용자나 브라우저 확장 프로그램이 볼 수 있다. 시연용이라 받아들인 한계다.
- 웹 화면은 연결한 노드를 믿는다. 단계와 입찰 상태를 노드에게 묻고, 공개할 때 입찰가와 secret을 노드로 보낸다. 거짓을 알려 주는 노드라면 입찰 기간 중에 공개를 보내게 만들어 secret을 받아 갈 수 있다. 그래서 노드 주소(`?rpc=`)는 이 컴퓨터의 노드(`localhost`, `127.0.0.1`, `[::1]`)만 받고, 노드의 실제 chain id가 배포 기록과 같은지 확인한다 (17번). 이 컴퓨터에서 도는 노드 자체가 악성인 경우는 막지 못한다.
- 최저가가 없으므로 입찰가 0도 유효하다. 유효 입찰이 0원뿐이면 0원에 낙찰된다.
- 로컬 Hardhat 네트워크 기준이라 블록 재구성(reorg)은 다루지 않는다.
- 경매 대상 NFT는 정상 동작하는 ERC-721이라고 가정한다. 판매자가 전송을 막는 NFT를 쓰면 종료가 실패해 낙찰자의 보증금이 묶일 수 있다.
- Indexer가 노드 재시작을 감지하는 방법은 시작할 때의 확인(9번)뿐이다. 노드를 다시 켜고 같은 주소에 다시 배포한 뒤 `indexer:reset` 없이 Indexer를 켰을 때, 그 사이 새 체인의 블록 수가 예전 책갈피를 이미 넘었다면 감지하지 못한다. 이때 Indexer는 예전 책갈피 다음 블록부터 읽어 그 앞의 새 이벤트를 놓치고, 예전 체인의 데이터도 DB에 남는다. 책갈피와 함께 그 블록의 해시를 저장해 두고, 시작할 때 체인에서 같은 번호 블록의 해시와 비교하면 체인이 바뀐 것을 알아내 막을 수 있다. 이번 범위에서는 만들지 않았다.

## 17. 시연용 웹 화면

발표 시연 때 경매가 진행되는 모습을 한눈에 보여 주기 위한 화면이다. 실제 서비스용 지갑 연동은 하지 않는다 (16번).

**구성**
- `web/` 폴더의 HTML, CSS, 순수 JavaScript(ES 모듈)로 만든다. 빌드 도구는 쓰지 않는다. 화면이 몇 개뿐이고, 설치와 빌드 단계를 늘리지 않으며, Express만 아는 사람도 설명할 수 있는 구성이기 때문이다.
- API 프로세스가 `express.static`으로 화면 파일을 제공한다. 화면과 API가 같은 출처라 CORS 설정이 필요 없고, 실행할 프로세스도 늘지 않는다. 파일을 내려줄 뿐이라 API는 조회 전용 그대로다 (11번).
- 화면 이동은 주소의 `#` 뒤만 바꾼다 (예: `#/auctions/0`). 서버에 화면용 경로를 둘 필요가 없다.
- 첫 화면은 "경매 진행"(B)이다. 위쪽 메뉴로 "경매 진행"과 "경매 목록"을 오가고, 검색창으로 사용자별 참여 경매를 연다.

| 화면 | 주소 |
|---|---|
| 경매 진행 (첫 화면, B) | `#/` |
| 경매 목록 (A) | `#/auctions`, `#/auctions?status=active` |
| 경매 상세 (A) | `#/auctions/3` |
| 사용자별 참여 경매 (A) | `#/users/0x…` |

**A. 조회 화면** (API만 사용, 쓰기 기능 없음)

| 화면 | 내용 |
|---|---|
| 경매 목록 | 상태, 진행 중·종료 필터, 다음 마감까지 남은 시간, 결과 |
| 경매 상세 | 단계 진행, 경매 정보, 결과, 입찰 목록 |
| 사용자별 참여 경매 | 그 주소가 참여한 경매와 그 사람의 입찰 |

- Outline의 "경매 조회" 요구사항에 대응하는 화면이라 조회만 한다. 참여(쓰기)는 B의 경매 진행 화면 한 곳에서 한다.
- 3초마다 API를 다시 불러오고, `asOf`의 블록이 바뀌면 다시 그린다. `asOf`가 15초 넘게 그대로면 "Indexer가 멈춘 것 같음"을 표시한다 (개발용 노드는 5초마다 블록을 만든다, 10번).
- 상태·결과 코드는 화면에서만 한국어 이름으로 바꾼다. API의 코드는 그대로다 (10번).
- API에서 받은 값은 `textContent`로 넣고 `innerHTML`에 넣지 않는다. 입찰자 주소 같은 값에 HTML이 섞여 있어도 실행되지 않게 하기 위해서다 (XSS 방지).

**B. 경매 진행 화면** (브라우저에서 컨트랙트로 직접)
- 쓰기는 브라우저에서 Hardhat 노드로 직접 보내고 API를 거치지 않는다 (3번). 노드가 열어 둔 테스트 계정으로 서명하므로 지갑이 없어도 된다. 노드 주소는 `http://127.0.0.1:8545`이고, 다른 포트의 노드는 화면 주소에 `?rpc=`로 준다.
  - `?rpc=`는 `http(s)://` 주소이고 호스트가 `localhost`, `127.0.0.1`, `[::1]` 중 하나일 때만 쓴다. 아니면 기본 노드에 연결하고 쓰지 않은 주소를 화면에 알린다. 다른 사람의 노드가 단계를 거짓으로 알려 주면 입찰 기간 중에 입찰가와 secret이 그 노드로 갈 수 있기 때문이다 (16번).
  - 연결할 때 노드의 실제 chain id(`eth_chainId`)가 배포 기록의 chainId와 같은지 확인하고, 다르면 연결하지 않는다.
- 7번 예시를 한 화면에서 처음부터 끝까지 진행한다. 화면을 오가거나 계정을 바꿔 고르지 않아도 된다. 보내기 전 확인과 안내 문구는 스크립트와 같다 (12번).

| 위치 | 내용 |
|---|---|
| 맨 위 | 현재 경매 번호, 단계 표시(입찰 중 → 공개 중 → 종료 대기 → 종료), "다음에 할 일" 한 줄, 다음 단계로 시간 넘기기 버튼, "새 경매 시작" |
| 가운데 카드 5장 | 판매자(계정 0번), A~D(계정 1~4번). 잔액, 장부, 이 경매에서의 상태, 단계에 맞는 버튼 하나 |
| 카드 아래 | 이 브라우저에 저장된 입찰 수, 내보내기·가져오기 |
| 아래 | 현재 경매의 입찰 현황과 결과. Indexer → API 기준이고, 공개 전 입찰가는 "비공개" (A와 같은 표). 결과 위에 "NFT 현재 소유자" |

- **현재 경매**는 체인의 가장 최근 경매다. 예전 경매는 A의 화면에서 본다.
- **NFT 현재 소유자**는 카드의 장부처럼 브라우저가 체인에서 바로 읽는다(`ownerOf`, API·DB에는 없음). 주소 대신 이름으로 쓴다: 경매 컨트랙트 주소면 "경매 컨트랙트 (보관 중)", 계정 0번이면 "판매자", 1~4번이면 "A~D", 그 밖은 짧은 주소. 생성 후에는 경매 컨트랙트, 종료 후에는 낙찰자(유효 입찰이 없으면 판매자)로 바뀐다 (4번).
- **새 경매 시작**: 판매자(계정 0번)가 경매에 올리지 않은 테스트 NFT를 갖고 있으면 그것을, 없으면 새로 발행해서 승인 후 경매를 만든다. 기간은 최소값(입찰 10분, 공개 1일)이다. 만든 경매가 바로 현재 경매가 된다.
- **카드 버튼**은 그 카드의 계정으로 보낸다. 계정을 고르는 드롭다운은 없다.

| 단계 | A~D 카드 | 판매자 카드 |
|---|---|---|
| 입찰 중 | 입찰가·보증금 입력 + 입찰, 장부가 0보다 크면 출금 | 장부가 0보다 크면 출금 (입찰 버튼은 없다. 예시에서 판매자는 입찰하지 않는다. 컨트랙트는 막지 않으므로 스크립트로는 할 수 있다) |
| 공개 중 | 공개, 장부가 0보다 크면 출금 | 장부가 0보다 크면 출금 |
| 종료 대기 | 종료 (누구나), 장부가 0보다 크면 출금 | 종료, 장부가 0보다 크면 출금 |
| 종료 | 출금 (장부가 0이면 꺼짐) | 출금 (장부가 0이면 꺼짐) |

- 출금은 컨트랙트가 언제나 받으므로(6번) 장부가 0보다 크면 단계와 상관없이 출금 버튼을 둔다. 출금하지 않고 "새 경매 시작"을 눌러도 앞 경매에서 받을 돈을 이 화면에서 출금할 수 있다. 출금 버튼은 단계의 버튼 옆에 따로 그려서, 생기거나 없어져도 입력하던 입찰 칸이 지워지지 않는다.

- **입찰 칸**에는 7번 예시 값을 미리 채운다: A 3/5, B 4/4, C 3/2, D 1/3 (입찰가/보증금 ETH, `npm run demo`와 같음). 바꿀 수 있다. D 카드에는 "예시: 공개하지 않음 → 보증금 몰수"를 적는다.
- **꺼진 버튼은 이유를 옆에 쓴다.** 예: "이미 입찰했습니다 (지갑당 한 번)", "입찰하지 않아서 공개할 것이 없습니다", "이 브라우저에 secret이 없습니다", "장부에 받을 돈이 없습니다". 다른 트랜잭션을 보내는 중에 누르면 그 이유를 알림에 쓴다.
- **다음에 할 일**은 단계와 입찰 수로 정한다. 예: "A~D가 카드에서 입찰합니다 (2/4명 입찰함). 다 입찰했으면 "입찰 마감으로"를 누르세요."
- **시간 넘기기**는 입찰 중이면 "입찰 마감으로", 공개 중이면 "공개 마감으로"다. 이 경매의 마감 시각에 블록을 하나 만든다 (12번 `time-travel`과 같음).
- 단계 표시와 카드는 노드에서 바로 읽는다(`phaseOf`, `getBid`, 장부). 컨트랙트가 받아 줄지를 판단하는 것이라 Indexer를 기다리지 않는다. 아래 입찰 현황은 Indexer 기준이라, 트랜잭션 직후 몇 초는 "화면 반영 대기 중"이 표시된다.
- 화면을 맨 위, 카드 하나하나, 아래로 나눠서 각자 보여 줄 내용이 바뀔 때만 다시 그린다. 3초 새로고침이나 다른 카드의 입찰 때문에 입력하던 값이 지워지지 않게 하기 위해서다.
- 카드(테스트 계정)와 시간 넘기기 버튼 옆에는 "로컬 테스트 노드 전용"이라고 표시한다.
- 입찰가와 secret은 브라우저 저장소(localStorage)에만 두고, 트랜잭션을 보내기 **전에** 저장한다 (8, 12번). 키는 스크립트 파일 이름과 같은 `<chainId>-<컨트랙트>-<경매 번호>-<입찰자>`다.
  - 저장소는 접속 주소(출처)마다 따로라서, `localhost`와 `127.0.0.1`을 섞어 쓰면 저장된 secret이 보이지 않는다. 같은 주소로만 접속한다.
  - 저장한 뒤 다시 읽어 확인하고, 저장하지 못하면 입찰을 보내지 않는다. 공개 전에는 저장값을 체인의 해시와 맞춰 보고, 맞지 않으면 보내지 않는다.
  - 저장소를 지우면 공개할 수 없으므로 내보내기(JSON)를 제공한다. 파일에는 secret이 들어 있다.
- ethers는 `node_modules`의 브라우저용 파일을 API가 `/vendor/ethers.min.js`로 제공한다. 백엔드와 같은 버전이고 인터넷 없이 시연할 수 있다. 컨트랙트 주소는 배포 기록을 `/deployment.json`으로 받는다. 스크립트와 같은 기록이다.
- (선택) 가져오기: 스크립트로 만든 `.bids/` 파일이나 내보낸 JSON을 브라우저 저장소에 넣어, 스크립트로 입찰하고 브라우저에서 공개할 수 있다. 지금 노드의 컨트랙트이고 입찰가·secret이 해시와 맞는 것만 넣는다. 이미 저장된 값이 체인의 입찰과 맞으면 덮어쓰지 않는다 (그 입찰의 secret이라서). 맞지 않거나 읽을 수 없거나 그 경매가 체인에 없으면 가져온 값으로 바꾼다. 노드를 다시 켜면 같은 컨트랙트 주소에 새 경매가 생겨 예전 값이 같은 키로 남기 때문이다.
